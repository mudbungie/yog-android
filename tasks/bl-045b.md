PROTOCOL 18 (yog bl-9ced) put `role` on every shape carrying a prepared
body. `prepare` answers null — litany's `worker`, spelled as an absence — and
the SEAT is what writes it back on the `/prompt` it deposits, so a planning
conversation is one field of a start rather than a lineage a workspace has to
author. bl-5070 vendored the field and carries the null through faithfully
(`codec::start`, asserted both directions); nothing on this device writes one,
so plan mode is startable from a seat that has the list and not from here.

## Why the chooser was not built with the vendor

The honest list of roles a workspace declares is **not a read on this wire**.
`reply/roles` answers which roles are ASSIGNED a provider and a model, which
is a different set from the ones the governing commit declares — a chooser
built from it would silently omit exactly the role somebody came here for, and
a control that cannot name its options is worse than none. A free-text field
beside the goal is the other shape and it is not obviously better: the engine
refuses an unknown role in band, so the失 failure is loud, but typing a policy
word into a chat composer is not a phone gesture.

## What this needs first

A read that answers the roles the governing commit DECLARES — which is a
question for yog's boundary, not a surface decision here. File it there, or
establish that `roles` already enumerates the declared set and this ball is a
chooser over `snap.roles` plus a null entry.

## Done when

Starting a conversation offers the role it will be born on, defaulting to the
absence, and the picked value rides the prepared body back unrewritten.
