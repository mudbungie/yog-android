Measured 2026-09-29 (bl-65dc cellular leg, three attempts over USB adb): after 'svc wifi disable' the app logged 'network changed' 34 s and 53 s later; the first call after the drop listed the wifi endpoints, and the first call after wifi returned listed the cellular ones — each a wasted rendezvous. Every call also listed the phone's own translator-side cellular address (25.x, unreachable from outside) and the stale wlan LAN address, and 'the entry's name did not resolve' appeared for a while after each change. Calls on wifi AND cellular carried '1 v6' although the internet network (wwan2 on cellular) has no v6 — candidates are the IMS network's v6 (unusable by apps) or the overlay ULA (fd7a::/64, unreachable from outside). Deliver: (1) detect the change from the platform, not from a periodic address diff — ConnectivityManager's default-network callback reaches Rust through the shell (the awake bridge from bl-c21d is the pattern) — and clear cached endpoints and the rest at once; (2) build the call's endpoint list only from addresses on the CURRENT default network's interface (the one the DHT socket sends from), never from all interfaces; drop ULA/link-local/overlay ranges (fc00::/7, fe80::/10, 100.64/10) — yog bl-f612 rules the overlay policy, but a ULA is never reachable from outside regardless; (3) say which v6 was included (family + scope class, no address). Tests on the fake bench with a fake network-change source: the call after a change carries only the new interface's addresses; a ULA is never listed.
