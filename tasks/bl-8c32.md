Round-1 multitenant lane, driving the phone seat on the x86_64 emulator.

## What happened

`adb install -r` of the APK sitting in `android/app/build/outputs/apk/debug/`
succeeded. Every launch then died before painting anything:

    java.lang.UnsatisfiedLinkError: No implementation found for
      java.lang.String dev.yog.Pocket.standing(java.lang.String)
      (tried Java_dev_yog_Pocket_standing and
       Java_dev_yog_Pocket_standing__Ljava_lang_String_2)
      at dev.yog.Pocket.standing(Native Method)
      at dev.yog.Pocket.arm(Pocket.java:153)
      at dev.yog.MainActivity.onResume(MainActivity.java:109)

and again from `Boot.onReceive`. The user sees "yog keeps stopping".

## What the artifact holds

    $ nm -D --defined-only lib/x86_64/libyog_android.so | grep Java_dev_yog
    (nothing)
    $ strings lib/x86_64/libyog_android.so | grep -c Java_dev_yog
    0

Zero of the five natives. A fresh `cargo ndk … build --release` on the same
tree produces a library that exports all five:

    Java_dev_yog_Lane_attending
    Java_dev_yog_Lane_wake
    Java_dev_yog_Pocket_serve
    Java_dev_yog_Pocket_standing
    Java_dev_yog_Watch_probe

So this was a stale `.so` married to a current dex — build hygiene, not a code
defect.

## The defect is that the gate said it was fine

    $ python3 scripts/apk-bridges.py <that same apk>
    bridges: 18 JNI name(s) over 5 class(es), both directions, against 4 dex file(s)
    EXIT=0

The check reads two directions and neither is this one: names the Rust crate
resolves must exist in the dex, and public static entry points in a pinned
class must be named by some Rust site. Both are about the crate talking INTO
Java. The third direction — a Java `native` declaration must be defined by a
symbol the APK's own `lib/<abi>/*.so` exports — is the one that fired here, and
it is the one whose failure is not a `NoSuchMethodError` on the first tool call
but a crash loop on first launch.

The module docstring states the motivation exactly, and it covers this case as
well as the two it implements:

    Nothing in a build checks any of it. … the first invocation of that tool
    answers a `NoSuchMethodError` on a device, which is the one place this repo
    cannot look.

The README goes further and promises the property this APK did not have:

    `make apk` now pins **every JNI name this crate resolves** against the dex
    it just built, both directions — a renamed Java method is a build failure
    instead of a `NoSuchMethodError` on somebody's phone

## Expected

`apk-bridges.py` enumerates the `native` declarations in the dex and asserts
each has a defining symbol in every `lib/<abi>/*.so` the APK packs — and fails
on an empty enumeration, the same two-direction discipline the script already
keeps for the dex scan. `nm -D` is not needed: the symbol names are readable
from the `.so`' dynsym with the zipfile module the script already imports, or
by `strings` as a floor.

## Severity

p2. The failure it misses is strictly worse than the two it catches — total,
immediate, and on every launch — and this run hit it on the first install
without doing anything unusual.
