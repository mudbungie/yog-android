Round-1 multitenant lane.

## Gesture and reply

    $ ANDROID_HOME=~/Android/Sdk make apk ABIS=x86_64
    cargo ndk -t x86_64 -o android/app/src/main/jniLibs build --release
        Finished `release` profile [optimized] target(s)
    cd android && gradle assembleDebug
    /bin/sh: 1: gradle: not found
    make: *** [Makefile:51: apk] Error 127

The Rust half had already run, so the failure lands after the long step.

## Why it is inconsistent rather than merely strict

`Makefile` line 32: `GRADLE ?= gradle`.

`scripts/deploy-phone.sh` resolves the same tool the way the README describes:

    And gradle is looked for in the two places one is actually found: `PATH`
    first, then the newest bin distribution under the gradle wrapper's own
    dists cache — a box that has ever run a wrapper has a whole distribution
    there and no `gradle` command.

That is exactly this box: a distribution under the wrapper dists cache and no
`gradle` on `PATH`. So `make deploy-phone` finds gradle and `make apk` — the
target `deploy-phone` itself builds through — does not.

The README does document the override (`make apk GRADLE=/path/to/gradle`), so
this is not undocumented; it is one resolution rule with two implementations,
and the more helpful one is in the script rather than in the target everyone
runs first.

## Expected

`apk` resolves gradle by the same rule `deploy-phone.sh` uses, which is already
written and already justified in the README. `GRADLE=` on the command line
still wins, unchanged.

## Severity

p3. One flag fixes it, and it is written down. It costs a build and a search
for the flag on every fresh checkout, and `make apk` is the first target in the
dev-loop list.
