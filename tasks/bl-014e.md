Android text input, root-caused and fixed in the throwaway GameActivity spike.
Both operator complaints (typing feels like call-and-response; backspace does
not repeat on long-press) are resolved and verified by adb-driven typing.

## 1. Typing latency — the poll was real, and it was 250 ms, not 16 ms

winit 0.30.13's android backend receives `InputEvent::TextEvent` (android-activity
synthesises it from the GameTextInput buffer) and drops it in a catch-all
`_ => warn!(...)` arm without requesting a redraw. Nothing produced a frame when
the IME committed, so the bridge could only notice new text on a timer.

The spike's own timer was worse than it read. `self.focus` was set by the widget
responses, reset to 0 immediately after the bridge call, and only the bottom
composer re-asserted it afterwards — so the two upper fields took the
*unfocused* 250 ms branch. That cadence is the call-and-response.

Key finding: no poll is needed at all. game-activity's native_app_glue
`onTextInputEvent` already calls `notifyInput()`, so the looper IS woken on every
IME commit — winit simply declines to turn that wake into a frame. Three lines in
a vendored winit android backend:

    InputEvent::TextEvent(_) | InputEvent::TextAction(_) => {
        self.redraw_flag.setter().set();
    },

`single_iteration` reads that flag a few lines below the input loop, in the same
iteration, so a commit produces a frame on its own edge. The spike now runs a
1 s heartbeat only (IME inset + counters) and text still lands immediately:
72–87 ms measured from an injected tap to the character being adopted, nearly all
of it the injection binary's own JVM startup plus IME processing.

Upstream: this belongs in winit. Full translation of TextEvent into winit `Ime`
events is blocked on semantics (the Ime vocabulary cannot express
`deleteSurroundingText`), but a wake-only arm is uncontroversial and dissolves
the poll for every consumer.

## 2. Backspace repeat — a games-activity bug, not editor state, not repeat rate

Ruled out first: the "the IME thinks the buffer is empty" hypothesis. Mirroring
the field back with `set_text_input_state` changed nothing.

Actual mechanism, from logcat with `setprop log.tag.gti.InputConnection VERBOSE`:
Gboard sends backspace as KEYCODE_DEL via `InputConnection.sendKeyEvent`, which
dispatches to the surface view's OnKeyListener — and games-activity 4.4.0's
`gametextinput.InputConnection.onKey` is, in effect:

    if (!getSoftKeyboardActive()) return false;
    if (processKeyEvent(event)) {
        stateUpdated(); immUpdateSelection(); restartInput(); return true;
    }

`InputMethodManager.restartInput` tears the InputConnection down and rebuilds it
— visible as `closeConnection` in the log — on EVERY key. The first delete
therefore destroys the connection Gboard's repeat loop is running against, so the
loop never starts. A plain EditText never restarts input on a keystroke.

Fix applied in the spike's Gradle shell, public API only, no reflection: install
our own OnKeyListener on the surface view AFTER the InputConnection constructor
has installed itself (`targetView.setOnKeyListener(this)`). For KEYCODE_DEL with
a collapsed selection it calls `deleteSurroundingTextInCodePoints(1, 0)` then
`endBatchEdit()` — endBatchEdit is what invokes the library's private
`stateUpdated()`, which is what wakes the native side — then
`imm.updateSelection(...)`, and swallows the event. No restartInput. Every other
key goes back to the stock listener, whose restart is harmless for a key that
does not repeat. Reaching the package-private `mInputConnection` needs one tiny
class declared in package `com.google.androidgamesdk`.

Result: a long press deletes at ~52 ms/char and stops cleanly at empty.

Upstream: the fix belongs in games-activity — drop `restartInput()` from `onKey`
or make it conditional. Until then every GameActivity app carries this defect.

## 3. TYPE_NULL — the editor was never a text field

GameActivity's default EditorInfo has `inputType = 0` (TYPE_NULL), which
android-activity's own docs describe as "the target input connection is not rich,
it can not process and show things like candidate text nor retrieve the current
text, so the input method will need to run in a limited 'generate key events'
mode". Calling `AndroidApp::set_ime_editor_info` per focused field
(TYPE_CLASS_TEXT | CAP_SENTENCES | AUTO_CORRECT, plus MULTI_LINE for a paragraph
field and SHORT_MESSAGE for a chat composer) makes the connection rich:
EditorInfo becomes `inputType=c001`, and autocorrect, the suggestion strip and
word prediction start working. This did NOT fix the backspace repeat on its own,
but it is required for normal typing quality. It must be set before a
restartInput; `setSoftKeyboardActive` and `setState` are the two calls that
trigger one.

Caveat found: the `TextInputAction` argument never reaches the IME. GameActivity's
`setImeEditorInfoFields` writes it to `EditorInfo.actionId`, but the enter-key
action is read from `imeOptions & IME_MASK_ACTION`; actionId is consulted only
when actionLabel is set. The enter key therefore stays UNSPECIFIED. The
workaround is to fold the action value into the ImeOptions bits — the
TextInputAction discriminants already equal the IME_ACTION_* constants. Not
applied: out of scope, and a Send key that does nothing would be worse than a
newline key, because winit drops `InputEvent::TextAction` too.

## 4. Bridge shape — the diff became a mirror

With a truthful editor the bridge needs no diffing, just two directions.
IME to app adopts the buffer wholesale; app to IME pushes the focused field's
text when the two have drifted (focus moved, a field was cleared). Wholesale
adoption is what makes a suggestion tap work: a 2-char word replaced by a 6-char
one in one step, which the old common-prefix diff mangled.

Three things the mirror needs.

- Focus must be read from egui at frame start (`ctx.memory(|m| m.focused())`),
  not remembered from the previous frame's widget responses.
- The push is ASYNCHRONOUS. `set_text_input_state` posts work to the Java UI
  thread, so the editor keeps reporting its OLD text for a few ms. Adopting in
  that window feeds stale text straight back into the field just pushed —
  measured: a focus change blanked the field for a frame. The bridge now holds
  the pushed text as a pending echo, refuses to adopt until the editor reports
  it (250 ms deadline, then re-push), and polls at 8 ms only inside that window,
  because a push we made ourselves generates no wake.
- Selection spans are UTF-16 code units (they index the Java Editable); egui
  counts chars. They agree on ASCII and diverge at the first emoji.

Also: the IME-inset JNI probe is six round trips and was running every frame. It
is now throttled to 200 ms — at the old 16 ms cadence that was ~375 JNI crossings
a second for a number that changes only when the keyboard slides.

## What this means for the gated tree

Three of the four fixes need no fork and are ordinary uses of android-activity's
public API: the editor-info call, the mirror shape, the echo guard. Two need
upstream work or a shim:

- the winit TextEvent wake — a fork today; a three-line upstream PR removes the
  need, and the gated tree forbids git deps, so it must land upstream or be
  replaced (below);
- the games-activity `onKey` restartInput — a ~40-line Java shim in the Gradle
  module today; belongs upstream.

Forkless substitute for the winit patch, if it is ever needed: a background
thread holding a cloned `egui::Context` plus a cloned `AndroidApp`, polling
`text_input_state()` at 4–8 ms while a field is focused and calling
`request_repaint()` the moment the buffer differs. It was not needed here and was
not built — the wake already exists, and using it is strictly better.
