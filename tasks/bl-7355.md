INVESTIGATED, NOT SHIPPED — the ball's own escape clause taken ("if egui's own text layout makes this heavy, say so on this ball rather than shipping a half-renderer"). What makes it heavy is not the layout API; it is the font set and a standing cross-client rule. Three findings and the two rulings needed.

## 1. The desktop renders NOTHING, and the ball's premise inverts

The ball says the desktop's precedent governs. It was read: lernie's whole transcript paint is `ui.strong(row.who); ui.label(row.said);` in src/ui/chat.rs — no markdown, no monospace, no code affordance, no wrap, and no markdown crate in its manifest (egui + eframe + rustls + serde_json is the entire dependency set). Its own doctrine is against restyling: 'a token this build does not know keeps its word and paints plain… a colour is a claim and the wrong claim is worse than none', and its transcript reply module states 'bytes ride as text… this holds exactly what the wire carried'.

So this app rendering markdown would not be following the desktop, it would be leading it — and DESIGN §7 here pins the opposite: 'The transcript is painted the way the window paints it… because two clients of one engine showing the same conversation two different ways is two readings of one fact.' Shipping the subset silently deviates from a stated invariant. RULING NEEDED (operator): may the phone lead on presentation, with an upstream ask filed against lernie so both clients converge? If yes, §7's sentence is amended by that ruling and this ball proceeds.

## 2. Bold cannot be bold in this app, and the gate forbids the usual fix

egui's TextFormat carries italics (a synthetic skew), a font family, a colour and a background — so italics, `code` spans and fenced blocks in monospace are all faithfully renderable today. Bold is not: there is no bold FACE in the bundled set (Ubuntu-Light proportional, Hack-Regular monospace, two emoji faces — none variable, so 0.36's variable-axis support has no axis to drive). egui's own 'strong' is a brighter colour, which is exactly the claim lernie's doctrine refuses.

The usual fix — commit a bold face — is structurally refused HERE: the disclosure gate rejects every binary it cannot read and BINARY_ALLOWED matches nothing, so a .ttf cannot enter this tree at all. The one open door is loading the platform's own face at boot (Android ships Roboto-Bold under /system/fonts), which needs no dependency and commits no binary — but it is a device-only path the host suite cannot verify, and it changes the app's typeface story. RULING NEEDED (operator): is a platform-font load the way to a real bold face? That is its own ball, not a p3's implementation detail.

Rendering `**bold**` as brighter ink instead is the half-renderer the ball forbids, and bold is the marker model prose uses most.

## 3. What is cheap, and why it was still not shipped alone

Code spans and fences alone ARE faithful today (Hack is bundled, and §13.2's wide-content rule — landed with bl-b62b — already says a fence gets its own horizontal scroller while prose wraps). But shipping backticks while asterisks stay literal answers half of the operator's sighting with the less visible half, and leaves the tree carrying a markdown parser that deliberately ignores the commonest marker.

## The shape, when it is unblocked

A pure span/block parser under the 100% floor (blocks: prose | fence; inline: plain | strong | italic | code) with the paint mapping spans to TextFormat in shell/chat.rs's body() — roughly 150 lines, and cheap. Previews stay plain per the pinned 160-character spelling either way. The parser's failure mode wants a test of its own: a literal asterisk in engine bytes must not be eaten, since these are verbatim payloads.
