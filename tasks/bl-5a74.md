The release run's `CI / android / apk` job fails at `Cross-clippy (the host
gate cannot see this cfg)` with exit 101, so the three steps after it — build
the APK, sign it, attach it to the release — never run and the §20 channel
publishes nothing. The engine already speaks 19, so the protocol gate is open
and this lint is the only thing holding v0.0.5.

    error: implicitly cloning a `String` by calling `to_owned` on its
           dereferenced type
      --> src/shell/controls/held.rs:103:62
          crate::shell::theme::line(ui, &[(scope.word().to_owned(), ink)])
      = note: `-D clippy::implicit-clone` implied by `-D clippy::pedantic`
    error: could not compile `yog-android` (lib) due to 1 previous error

**The trailing `note: rustup target install aarch64-linux-android` in the log
is cargo-ndk's, not the cause.** cargo-ndk prints it after ANY non-zero cargo
exit; both android targets are pinned in `rust-toolchain.toml` and the log
shows the crate compiling for `aarch64-linux-android` before the error. The
cause is one clippy pedantic denial.

`Scope::word()` changed from `&'static str` to `String` in the PROTOCOL 19
landing — the `Unknown(String)` arm cannot answer a `'static` str — and the
`held.rs` caller's `.to_owned()` became a `String::to_owned()`, which
`clippy::implicit_clone` denies. The host gate never sees it: the whole
`src/shell` tree is `#[cfg(target_os = "android")]`.

## This is the second time, and the site is not the defect

bl-3d34 was the same failure two days earlier (`field_reassign_with_default`
in `shell::theme::install`) and fixed only its site. The structural cause is
that **the gate that decides a landing cannot see this code**. Work lands on
`main` by `bl close`, whose gate is `make check`; `make check` runs
`cargo clippy` for the host only. `ci.yml` has no `push` arm by design
(bl-7a68), so the android leg's verdict arrives on the release run — after the
landing, on a tree nobody can un-land. Every android-only lint denial is
therefore found by the release it breaks.
