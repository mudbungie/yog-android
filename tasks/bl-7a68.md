Operator ruling 2026-09-05: *all of my devices should be running effectively
full CD — any new publication should result in an upgrade of the running
versions.* After the round-1 CICD lane every device but this one does:

  * the always-on engine box runs the OCI image under `yog.service` with a
    15-minute `yog-reconcile.timer` off `ghcr.io/mudbungie/yog` (yog DESIGN
    §10.1);
  * a workstation runs the native binary under the same unit name with an
    hourly reconciler off the crates.io sparse index (yog bl-8ea9, DESIGN
    §10.1.1);
  * the seat installs the newest live `lernie` hourly and the next window
    launch adopts it (lernie bl-155a, local carrier bl-bae7);
  * the foot does the same for `thrall` and defers a restart while an
    invocation executes (thrall bl-6c98).

Every one of those is: **read the newest live version off a registry, compare
it with what is installed, install if it differs, restart only when the box
says it is idle.** Four of the five components already answer it.

The phone answers none of it. `make deploy-phone ADDR=<ip:port>` is
push-on-demand over adb wireless debugging, and the Makefile already states the
honest limit: *"no scheduler can supply an address a human has to read off the
phone"*. The port rotates on every re-pair and reboot. So the phone is upgraded
only when somebody is holding it AND at a workstation AND remembers, and its
build is a debug-keystore APK that no distribution channel would accept anyway.

### What is different about this device, and what is not

**Not different:** the version question. There is one publication event per
version and the phone can read it, so "is there something newer" is the same
query the other four make.

**Different, and it is one thing:** Android will not let a process replace
itself. An unattended install needs either a privileged installer, a device
owner, or an app-store channel — none of which this is. The most an app may do
is *ask*: `ACTION_VIEW`/`PackageInstaller` puts the system installer in front of
the person, who taps. So the phone gets the same reconciler with the last rung
replaced — **detect and offer, never install.**

### The shape to design

1. **The publication.** yog's release workflow already builds a
   `yog-x86_64-unknown-linux-gnu` archive and attaches it to the `v<version>`
   GitHub Release (`.github/workflows/release-plz.yml`, the `release-binaries`
   job). This repository has no release workflow at all — `ci.yml` and
   `store-scan.yml` are the whole of `.github/workflows/`. The ask is a job on
   the release tag that assembles a **signed** APK and attaches it as a Release
   asset, so the feed is `GET /repos/<owner>/<repo>/releases/latest` and the
   artifact is one URL under it.
2. **The signing key, and it is the blocking decision.** `make apk` signs with
   the debug keystore today. A release channel needs a real key, and an Android
   signing key is not rotatable: a device that installed under key A refuses an
   update signed by key B, and the remedy is uninstall-and-reinstall, losing
   app state. So this is an operator act with a permanent consequence, and it
   is exactly what AGENTS.md means by *"an APK release channel gets its own
   checklist ball before the first APK leaves this box"*. It also may not live
   in this tree: the leak gate refuses any binary it cannot read and
   `BINARY_ALLOWED` matches nothing, so a keystore is a repository secret and
   never a committed file.
3. **The read.** The app asks the Releases feed on a cadence it chooses — on
   resume is probably right, since a phone app has no timer worth the battery —
   compares the tag against its own `versionName`, and does nothing at all when
   they match. Anonymous and unauthenticated, like every other box in the fleet:
   a device holds no registry credential, and that is the property that makes
   the whole channel possible rather than a place to park a token.
4. **The offer.** A version that differs surfaces ONE affordance, and the design
   question is where. It is not a modal on launch — the phone seat is a working
   surface and an update prompt in front of a live conversation is the failure
   this whole suite's notice discipline exists to avoid. A row in the same
   place the seat already says structural things about itself is the candidate.
   Tapping it downloads the asset and hands it to the system installer; the
   person taps again. Two taps and no surprise.
5. **What must NOT be built.** No silent install, no self-update path, no
   background download on a metered connection, and no version list — one live
   version, the newest, exactly as the other four reconcilers read it. And no
   downgrade: crates.io yank is the fleet's rollback lever and a GitHub
   Release has no equivalent, so the rollback story here is "delete the release
   and publish another", which should be stated rather than implied.

### The protocol-skew consequence, which is already live

A seat that updates ahead of its engine speaks a newer `PROTOCOL`, and yog
REMOTE §9.5's hello is fail-closed: the refusal names both versions and the
window will not paint. Every other box closes that skew within the hour on its
own. **A phone cannot**, because the last rung needs a tap — so a phone whose
person is not holding it stays skewed indefinitely, and the refusal it shows has
to say so in a way that names the act (update the app) rather than the fault.
That is a design constraint on the refusal text, not just on the updater.

Do not implement this round: the signing-key decision (2) gates everything after
it and is the operator's alone.

Operator ruling 2026-09-05: one permanent signing key for the app's lifetime. Generated: PKCS12 keystore at ~/keys/yog-android/release.keystore (alias yog-android, RSA 4096, 100-year validity) with the password beside it in release.keystore.password and a README; the operator backs the directory up offline. Implementation: CI reads the keystore base64 from the repo secret ANDROID_RELEASE_KEYSTORE and the password from ANDROID_RELEASE_KEYSTORE_PASSWORD (set them with gh secret set from that directory), signs with APK Signature Scheme v3 so a future rotation can carry a lineage, and the first release-signed install replaces the debug-signed APK on the phone once (uninstall + re-enrol).
