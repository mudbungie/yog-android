Operator ruling 2026-08-30 (yog bl-15bd): the Android app is named **yog** and
ships all three runnable components — the seat, the foot, and the server —
**each gated behind an explicit bootstrap rather than auto-started**. The
default bootstrap path is mTLS client enrolment (seat or foot dialing a host
engine, material provisioned out of channel per REMOTE §1.4); running the
server locally on the phone is allowed but is the deliberate, non-default
choice. The existing development client app is superseded — its landed
foundations are the starting material, not discarded work.

**What the rename touches.** The label the launcher paints, and the
`applicationId` the package manager keys an install on. This app has never
left the box that builds it and has no upgrade path to preserve, so the id
moves freely; a later install channel makes that a one-way door, and that is
the reason to move it now rather than after.

**The first-run surface is the bootstrap chooser**, and it is a surface
because the ruling says the components are *gated*: an app that picked one
would have made the operator's choice for them, and an app that started all
three would have made it three times. Enrolment carries the emphasis — it is
the default path, and the other two are reached from the same screen rather
than from a menu that implies they are settings.

**Enrolment is not a protocol.** REMOTE §1.4 stands and DESIGN §5 restates it:
the new device never enrols over its own unauthenticated connection. What the
app offers is the *import* of material placed there through existing trust,
and the material's shape is REMOTE §8.2's entry — `ca.pem`, `client.pem`,
`client.key`, `address`, and the optional `workspace` naming what the entry is
called on its host when that differs from the local leaf. The flat directory
this client reads today is the zero-entry case of exactly that shape.
