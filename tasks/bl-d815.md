The enrollment screen wants **Scan QR** beside the paste field (bl-dd7b). Decoding a QR from the camera needs a decoder, and the honest evaluation is that **the platform ships none this app can reach** — so this is rule 6 territory: *"Zero new dependencies without explicit operator approval."*

**What was looked for and what is there.**

- **AOSP framework**: no barcode or QR decoder in any public API. `camera2`/CameraX give frames; nothing in the platform reads one. There is no `ACTION_SCAN_BARCODE` a stranger app may rely on, and routing through the system camera app or Lens is a hand-off to whatever happens to be installed, with no contract and no result on devices without it.
- **ML Kit barcode scanning**: the route everyone means by "the platform route". It is **not** platform: it is Google Play Services, a Gradle dependency tree this repo has never had, several MB in the APK for the bundled model, and absent on a device without Play Services. It also brings CameraX or a camera2 pipeline with it.
- **ZXing**: third-party, either as `com.google.zxing:core` (Java, into the Gradle module) or `rxing` (a Rust port, into `Cargo.toml` — which is where this crate's gate can actually judge a dependency: `cargo-deny` reads licenses, advisories, sources and bans, and the Gradle side has no equivalent gate at all).
- **From scratch**: a Reed-Solomon decode behind a binarizer, a finder-pattern locate and a perspective unwarp. Buildable, testable, and not a small evening — and it would be new code under the 100% floor for a format that has three mature implementations.

## The ruling (operator, 2026-08-30): `rxing`

ML Kit is refused — the Play Services coupling is a change to the shape of the APK, not a convenience. From-scratch is refused — three mature implementations exist and this repo would maintain a fourth forever. **`rxing` is taken because the decoder then lives where the gate can see it.** The manifest line carries the reasoning verbatim; DESIGN §12.1 carries the ruling.

What it actually cost, measured rather than assumed: **no new license** (Apache-2.0 was already allowed for ring's AND-arm; rxing carries it outright), **no advisory**, **no C toolchain**, and a pure-Rust subtree of chrono / num / once_cell / regex / thiserror / unicode-segmentation / encoding_rs / codepage-437. The feature set is the smallest one that decodes: `qrcode` + `decoders` + `encoding_rs`, with `image`, `encoders` and every other symbology off. `encoding_rs` is not optional in practice — rxing's only other character-set arm, `no_character_set_support`, compiles `CharacterSet::decode` to `unimplemented!()`, which byte-mode QR content reaches on every decode and which rule 4 forbids.

## The capture route: camera2 in the Java shell, no preview surface (DESIGN §12.2)

Two routes were live — the NDK camera API from Rust, or camera2 in the Java shell. The Java shell wins on machinery already present: this repo has a proven JNI bridge with the class-loader trap already solved, while the NDK route needs a new dependency or raw FFI, and rule 3 confines every `unsafe` to `sys.rs`.

The session has **exactly one output and it is an `ImageReader`** — no `SurfaceView`, no `SurfaceTexture` into wgpu, no CameraX — because the Rust side paints the preview from the very buffer it decodes. The egui frame loop keeps the one surface it already owns, and the class of defects where the preview works but the decoder sees something else cannot arise. Rust pulls, Java never calls in (a Java to Rust callback is another `no_mangle` entry point).

`src/scan.rs` is the whole Rust surface: a frame in, `Option<String>` out. **It is a producer, not a second sink** — the decoded string goes into the paste field and is spent by `envelope::read` + `envelope::land`, so the version check, the grade-versus-certificate law and every refusal sentence are reached by one path however the text arrived.

## What the emulator taught (both were defects, both fixed before landing)

- **A fresh ~900 KB array per frame killed the app**: `OutOfMemoryError` on the camera's `HandlerThread`, whose death is the process's. Frames are now packed only when the reader has taken the last one, into one of two alternating buffers, so steady-state allocation is zero; the packer catches even `OutOfMemoryError`, because a sentence beats a stack trace only logcat sees.
- **The permission must be asked per tap, not per process**: `checkSelfPermission` cannot tell "the dialog is up" from "the operator said no", so a remembered refusal made the second tap answer with the first tap's sentence and no dialog — while the platform's own rule is that one denial is not final.

## Proof

- **Decode fixtures**: one symbol encoded by `segno` — an independent ISO/IEC 18004 implementation, so the decoder is not tested against its own writer — at REMOTE §8.4's own bar: 1567 bytes of compact JSON, version 33, level M, 149x149 modules. Checked in as its module matrix plus the payload; the envelope is a throwaway `notreal-` PKI whose two certificates are public material and whose `key` field is fabricated filler with no private-key banner.
- **The whole path is one host test**: a camera-shaped frame decodes to the exact bytes, those bytes go through the real sink, and the component that comes up is the one the certificate says. It also reads at two pixels per module, which is the floor.
- **Emulator, virtual-scene route**: the QR rendered as the scene's wall poster (`adb emu virtualscene-image wall`, aimed with the stock `Walk_to_image_room` macro), decoded off the live camera. Launch to Thrall to Scan QR to permission to decode to validated to the foot component up under the certificate's own name. The denial branch was driven too and lands on the paste field with its sentence.

Residual: none for this ball. A device with no camera or a permanently-denied one falls to the paste field, which is the degraded path bl-dd7b already proved.
